# ประสิทธิภาพ: เว็บนี้รับโหลดได้แค่ไหน และรับด้วยอะไร

เอกสารนี้อธิบายชั้นต่าง ๆ ที่ทำให้ dashboard เร็วและไม่ล้ม HosXP
พร้อมบอกว่า "ถ้าอยากรับโหลดมากกว่านี้ ต้องไปแตะตรงไหนต่อ"

## เข้าใจตัวเลขก่อน

| โหลด               | เฉลี่ยต่อวินาที      | ต้องมีอะไร                                 |
| ------------------ | -------------------- | ------------------------------------------ |
| 1 ล้าน req/วัน     | ~12 req/s (พีค ~100) | เครื่องเดียว + ชั้น cache ในเอกสารนี้ = พอ |
| 1 ล้าน req/ชั่วโมง | ~280 req/s           | เพิ่ม replica 3–4 ตัว + reverse proxy      |
| 1 ล้าน req/นาที    | ~17,000 req/s        | ต้องมี CDN/edge cache หน้าบ้าน             |

ของจริงของโรงพยาบาลอยู่แถวแถบแรก — ชั้น cache ปัจจุบันเอาอยู่สบาย
ส่วนที่ต้องระวังไม่ใช่ "จำนวน request" แต่คือ **จำนวน query ที่หลุดไปถึง HosXP**

## ชั้นที่มีอยู่ (จากนอกเข้าใน)

1. **เบราว์เซอร์** — ทุก API ที่เป็นข้อมูลอ่านอย่างเดียวส่ง `ETag` + `Cache-Control: private`
   - อยู่ในช่วง `max-age` → เบราว์เซอร์ไม่ยิงเลย
   - เลย `max-age` → ยิงพร้อม `If-None-Match` แล้วได้ **304 ตัวเปล่า** (payload 120 KB → 0 byte)
   - โค้ด: `lib/httpCache.ts`
2. **การ poll ของหน้าเว็บ** — `lib/visibleInterval.ts`
   แท็บที่ถูกซ่อนอยู่จะไม่ยิง และจะยิงชดเชยทันทีที่ผู้ใช้กลับมาดู
   (จอทีวีที่เปิดค้าง/แท็บที่เปิดทิ้ง ไม่กิน traffic ตอนไม่มีคนดูอีกต่อไป)
3. **Redis (payload cache)** — `cachedJson()` ใน `lib/cache.ts`
   เก็บ **ตัว response ที่ gzip แล้ว** ไม่ใช่ object ดังนั้นทุก cache hit
   ไม่มีการ `JSON.parse`/`stringify` เลย — CPU ต่อ request แทบเป็นศูนย์
   (ทดสอบจริง: payload 121 KB → 10.7 KB บนสาย = 9%)
4. **Stale-while-revalidate + stampede lock** — หมดอายุแล้วยังแจกของเก่าได้อีก 3 เท่าของ TTL
   และตอน cache ว่างพร้อมกัน 50 request จะมี **query จริงแค่ครั้งเดียว**
5. **Cache warmer** — `lib/cacheWarmer.ts` อุ่น endpoint หนักไว้ก่อนหมดอายุ
   โหลดบน HosXP จึงเป็น "ค่าคงที่ต่อรอบ" ไม่โตตามจำนวนผู้ใช้
   รันหลาย replica ได้: มีการเลือก leader ผ่าน Redis ให้ replica เดียวเป็นคน warm
6. **เพดานความเสียหาย** — `lib/limiter.ts` + pool ใน `lib/db.ts`
   query หนักวิ่งพร้อมกันได้ไม่เกิน `DB_HEAVY_LIMIT` (ค่าเริ่มต้น 6)
   ต่อให้ Redis ล่มทั้งก้อน request ก็ไม่ไหลเข้า HosXP พร้อมกันเป็นร้อย

## ตัวแปรที่ปรับได้ (env)

| ตัวแปร           | ค่าเริ่มต้น | ความหมาย                                           |
| ---------------- | ----------- | -------------------------------------------------- |
| `DB_POOL_SIZE`   | 12          | connection สูงสุดต่อ pool (มี 2 pool: `db`, `db2`) |
| `DB_POOL_IDLE`   | 6           | connection ที่ถือไว้ตอนว่าง                        |
| `DB_QUEUE_LIMIT` | 200         | คิวรอ connection ยาวเกินนี้ = ตอบ error แทนค้างยาว |
| `DB_HEAVY_LIMIT` | 6           | query หนักพร้อมกันสูงสุด                           |
| `CACHE_WARMER`   | เปิด        | ตั้ง `0` เพื่อปิด warmer                           |

## ถ้าจะไปต่อ (เรียงตามความคุ้ม)

1. **ETL แทน live query** — ดึงจาก HosXP มาลงตารางสรุปในเครื่องตัวเองทุก 5–15 นาที
   แล้วให้ dashboard query ตารางสรุป: query จากหลักวินาทีเหลือหลักสิบมิลลิวินาที
   และโหลดบน HosXP คงที่จริง ๆ ไม่ว่าจะมีคนใช้กี่คน
2. **หลาย replica** — leader lock พร้อมแล้ว เหลือแค่ scale service `app` แล้ววาง
   reverse proxy (Caddy/nginx) หน้าบ้าน เพราะ Node ใช้ CPU ได้ core เดียวต่อ process
3. **SSE/WebSocket แทน polling** — จอทีวีหลายจอ poll เองทุกจอ เปลี่ยนเป็น push ทางเดียว
4. **วัดผล** — เก็บ cache hit rate / เวลา query ต่อ endpoint แล้ว expose เป็น metrics
   จะได้รู้ว่าควรแต่ง TTL ตรงไหน แทนการเดา
